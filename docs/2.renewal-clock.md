The module decides on its own when a subscription needs a charge. That is the
reason it exists. It is also the part that has to be right when several
instances run at once and any of them can die in the middle of a charge.

## The database decides and the clock only triggers

Every subscription record carries `dueAt`, the time when it next needs
attention. A trigger has one job: make an instance look at the records whose
`dueAt` has passed. The instance reads what to do from the record, never from
the trigger. It charges the next period, retries a failed one, reads a
settling charge again, or ends the subscription at period end.

Whichever trigger runs, the database holds the same information. If Redis
never fires a renewal, the next sweep still makes it.

## Choosing the trigger

At start, before the module touches Redis at all, it picks one of two
triggers:

1. If `@antelopejs/interface-redis` or `@antelopejs/interface-redis-scheduler`
   has no implementation wired, the module **polls**. It sweeps the database
   every `pollIntervalMs`, so a renewal is charged at most one interval late.
2. Otherwise the module **uses the Redis scheduler**. Each subscription is one
   task, named after the subscription and fired at its `dueAt`. When `dueAt`
   changes, the module schedules the task again, and when `dueAt` is cleared, it
   removes the task. A sweep still runs every `sweepIntervalMs`, because the
   scheduler drops a task whose handler dies mid-run, and the database alone
   must be enough.

The Redis interfaces are optional dependencies, and the module imports them
lazily after the wiring check. Nothing on a request path or in `start()` waits
for a Redis connection. A Redis that is wired but unreachable delays renewals
until the next database sweep, and it blocks nothing.

The suite checks the Redis scheduler through normal interface routing, without
a test-only bypass for handler registration. If the scheduler refuses to
register the handler, the module logs a warning and falls back to polling. At
start, the module logs which clock it chose, and `ActiveClock()` returns
`"polling"` or `"redis"`.

## Claiming a renewal

Several instances can find the same renewal due. The module changes each record
only with a conditional write against its current revision (`atomicMutation`),
and a charge starts with one:

1. Read the record. If it is not due, or the claim of another instance on it
   has not expired, leave it.
2. Write a claim against the revision just read. The claim names this instance
   and lasts until now plus `leaseMs`. Of several instances that read the same
   revision, exactly one write succeeds. The others stand down without a call
   to the provider.
3. Charge.
4. Read the record again and write the outcome against its current revision.
   Then deliver the events and release the claim.

If a cancellation lands between step 2 and step 4, step 4 applies the outcome
to the record as it is now. A charge that went through on a subscription that
was just cancelled is recorded and reported, and the subscription stays
cancelled.

## When an instance dies mid-charge

The claim of that instance expires after `leaseMs`, and another instance claims
the renewal. Before the first provider call, the module persists the payment
method, `attemptStartedAt`, and `attemptReplayUntil`. A takeover sends the same
idempotency key only strictly before that deadline. The deadline comes from
`guaranteedReplayMs`, which defaults to zero, and a later configuration change
never extends it. A lease is not an idempotency guarantee. Configure a
conservative retention duration, with enough margin for clock skew, request
latency, and process stalls across all instances.

If the result is still unknown after the protection expires, processing halts.
The subscription reports `vendorData.reconciliationRequired: true`, and the
module logs an error that contains the subscription ID. A record whose attempt
has already started but carries no attempt timing does not get a new replay
window. It halts for reconciliation too. The module reads a known pending
payment by its ID, even after the deadline, and that read never submits a
charge. For the operational recovery procedure, see
[failed renewals](./3.failed-renewals.md#reconciliation-and-operational-recovery).

The deadline is the second guard. The first guard, the claim, means that the
provider normally never sees a second request at all.

## Several instances

No instance keeps anything in memory that another instance needs. Each
instance has its own claim identity, sweeps on its own, and delivers the
events of the records it processed to the handlers registered in it. Any
number of instances can run against one database.

## Testing the clock

The clock that the module reads is replaceable (`UseClock` in `src/clock.ts`),
and the suite drives a manual clock through trials, renewals, failures,
retries, and period ends. Separate tests check the real triggers in real time:

- A renewal made by polling, with nobody calling.
- With Redis, a task scheduled for the end of a trial and fired by Redis while
  the sweep is an hour away.
- With Redis, a task deleted from Redis whose renewal the sweep still makes.

A boot test launches a project the way production does, without the test
harness, and checks that it starts and renews.
