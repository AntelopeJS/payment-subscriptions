title: Failed renewals
description: The retry policy of this module for declined renewals, settling charges, refusals, an unreachable provider, the first period, and reconciliation.

The interface promises only that a failed renewal is reported as `past_due`.
What happens next is the policy of each implementation. This page describes
the policy of this module.

## The policy

When the charge for a period is declined:

1. The period advances anyway, the subscription goes `past_due`, and the module
   raises `subscription.payment_failed`. The unpaid period is the current one.
2. The module retries the charge after each entry of `retryDelaysMs`, measured
   from the failure before it. By default the delays are one day, three days,
   and seven days, which makes four attempts over eleven days.
3. A retry that succeeds makes the subscription `active` again, in the same
   period. The cycle does not move.
4. When the last retry fails, the subscription ends. It becomes `canceled`,
   with `endReason: "payment_failed"`, and the module raises both
   `subscription.payment_failed` and `subscription.canceled`.

A payment with the status `failed`, `canceled`, or `requires_action` counts as
a decline.

Each new attempt uses the payment method of the subscription at the time of
the attempt. A payer recovers by calling `UpdateSubscriptionPaymentMethod`
during `past_due`. Each attempt has its own idempotency key. A retry is a new
charge, not a replay of the decline.

A subscription set to end at period end keeps being retried until its period
ends. Then it ends, and the module retries no further.

## A charge that is still settling

A bank debit can report `pending` for days. The module treats a payment with
the status `pending` or `authorized` as settling. The subscription keeps its
status: `active` after a trial or a paid period, or `past_due` during retries.
The module reads the charge again every `settlementPollMs` until it settles,
then treats it as succeeded or declined. Nothing is reported until it settles.

If the subscription is cancelled while a charge is settling, the module still
follows the charge. A charge that then succeeds is recorded and reported, so
that the merchant can refund the money.

## A provider that refuses the charge

`CustomerNotFoundError`, `PaymentNotFoundError`, `InvalidPaymentStateError`,
and `UnsupportedOperationError` from the payment interface mean that the
provider will not make this charge. The most common cause is a saved method
that has been removed. They count as a declined attempt. The subscription goes
`past_due`, the module retries it under the policy, and it ends when the
retries are spent. The `subscription.payment_failed` event has no `payment`,
because no payment was made.

If one of these errors comes back when the module reads a settling charge, the
module does not count it as a decline. It holds the subscription for
reconciliation.

## A provider that cannot be reached

Any other `PaymentError` is not a decline. The charge is in doubt. The module
can make the same attempt again after `errorBackoffMs`, but only within the
persisted provider guarantee. The retry uses the same idempotency key **and
the same payment method**, both recorded before the first try. If the first
request did reach the provider, the retry finds that charge instead of making
another, even if the method was changed in the meantime. The new method is
used from the next attempt. With the default `guaranteedReplayMs` of zero, the
guarantee has already expired, so the module holds the subscription for
reconciliation instead of retrying.

If the subscription is cancelled while a charge is in doubt, the module does
not make the attempt again, and it holds the record for reconciliation. A
charge that did land then reaches the merchant only as the
`payment.succeeded` webhook of the payment interface, which carries
`antelopeSubscription`.

## After a stall

Periods are counted from the anchor. If the module could not process a
subscription for longer than a period, because the database or every instance
was down, it charges every missed period on recovery, one after another.

## The first period

When the request has neither `trialEnd` nor `billingAnchor`,
`CreateSubscription` charges the first period itself, and a decline there
creates no subscription. A declined payment rejects with
`SubscriptionPaymentError`. A refusal from the provider, with no payment made,
rejects with `InvalidSubscriptionRequestError`. A payer with no subscription is
not `past_due`. With `trialEnd` or `billingAnchor`, the module creates the
subscription at once and charges the first period at that time, under the
policy above.

A creation that ends without an answer must be replayed with the same
idempotency key. That happens when the provider could not be reached, or when
the instance died during the call. The replay resumes the creation only within
its persisted replay window. After the window expires, the replay rejects with
the error `Subscription <id> requires reconciliation; charge replay protection unavailable or expired`
and does not charge again. A refused creation stays refused on replay. The
module never completes a creation that nobody replays, and a charge that such
a creation made belongs to no subscription. That charge still reaches the
merchant as a webhook of the payment interface that carries
`antelopeSubscription`.

## Reconciliation and operational recovery

`guaranteedReplayMs` defaults to zero. The module makes the first call, but it
does not replay an uncertain result blindly. Set a positive value only from a
documented provider guarantee that covers every account that uses this module,
with a safety margin. The module retries transient errors only strictly before
the saved deadline. Declines follow the separate, finite `retryDelaysMs` policy
with new attempt keys.

Live subscriptions expose `reconciliationRequired`, `attemptStartedAt`,
`attemptReplayUntil`, and `phase` in `vendorData`. A halted record has no next
charge scheduled. Cancellation and payment method changes do not clear the
hold. An initial creation is not a public live subscription yet, so it exposes
the hold through the replay error and the persisted record.

To recover a halted subscription:

1. Stop all module instances and triggers, and drain the requests in flight.
   Back up the record, and keep its revision, provider account, attempt key,
   timing, and payment method. Never delete the record or reset its timing to
   force a replay.
2. Search the authoritative ledger of the provider, including webhooks and the
   metadata key `antelopeSubscription`, with the original account and attempt
   key. If the result is still unknown, leave the hold in place and escalate to
   the provider.
3. If you find a payment, verify its customer, method, amount, currency,
   subscription metadata, and original attempt key. Recover the target period
   index from that key (`payment-subscriptions:<id>:<period>:<attempt>`), not
   from the last paid period of the record. If you cannot establish the target,
   leave the hold in place.
   An operator-reviewed database repair, conditional on the revision, can
   attach that ID as `pendingPayment`, clear `reconciliationRequired`, and set
   `nextActionAt` and `dueAt` to now with the lease cleared. Set `periodIndex`
   to the recovered target for every record, renewals included. The initial
   charge targets `0`. For a `creating` record, replay the original creation
   key, and the module reads that payment instead of charging. For a live
   record, restart processing so that the module reads and applies the actual
   status of the payment. Keep the original attempt identity and timing intact.
4. If the provider proves that no charge exists, prefer to retire the held
   subscription and create a replacement with a new key, under an audited
   merchant decision. Do not retry the uncertain attempt silently. Resolve any
   provider schedule registration as well. Refunds and entitlement corrections
   stay merchant operations.

The module has no portable force-retry or reconciliation API, on purpose. A
database repair needs evidence from the provider and an audit trail. An
elapsed lease, a method update, or a longer configuration value is not
evidence of non-payment.
