# The renewal clock

The module decides on its own when a subscription needs charging. That is the
whole reason it exists, and the part that has to be right when several instances
run at once and when any of them can die mid-charge.

## The database decides, the clock only knocks

Every subscription record carries `dueAt`: when it next needs attention. A
trigger's only job is to make an instance look at records whose `dueAt` has
passed. What to do is read from the record — charge the next period, retry a
failed one, read a settling charge again, end it at period end — never from the
trigger.

So whichever trigger runs, the database holds the same information, and a
renewal Redis never fires is still made by the next sweep.

## Choosing the trigger

At start, before touching Redis at all:

1. If no module implements both `@antelopejs/interface-redis` and
   `@antelopejs/interface-redis-scheduler`, **poll**: sweep the database every
   `pollIntervalMs`. A renewal is charged at most one interval late.
2. Otherwise **use the Redis scheduler**: each subscription is one task, named
   after it and fired at its `dueAt`. Rescheduling replaces the task. A sweep
   still runs every `sweepIntervalMs`, because the scheduler drops a task whose
   handler dies mid-run and the database alone must be enough.

The check comes first because an interface nobody implements does not fail its
calls, it queues them: a module that awaited a Redis client nobody provides would
hang in `start()` for ever. The Redis interfaces are optional dependencies,
imported lazily after the check, and nothing on a request path or in `start()`
awaits Redis. A Redis that is wired but unreachable delays renewals until the
next sweep; it blocks nothing.

### The scheduler, as published, refuses the handler

With `@antelopejs/redis` 1.0.3, `@antelopejs/interface-redis-scheduler` 0.0.7
and AntelopeJS core 1.10.2, the scheduler's `setHandler` throws
`MissingProviderError` from any module other than the scheduler's own tests. Its
handler registry is a registering proxy, and the redis module, which declares it
implements the scheduler, never attaches a provider for it. Without a handler
`addTask` cannot be called, so there is no Redis clock to use.

The module catches that, logs it, and **polls instead**. It starts, and it
renews. Redis-triggered renewals are verified only with the handler registered
outside the runtime's routing, in the suite.

## Claiming a renewal

Several instances may find the same renewal due. Each record is changed only by
a conditional write against its current revision (`atomicMutation`), and
charging starts with one:

1. Read the record. If it is not due, or another instance's claim on it has not
   expired, leave it.
2. Write a claim — this instance, until now plus `leaseMs` — against the revision
   just read. Of several instances that read the same revision, exactly one
   succeeds. The rest stand down without reaching the provider.
3. Charge.
4. Write the outcome against the claimed revision, then deliver the events and
   release the claim.

If a cancellation lands between 2 and 4, the write in 4 conflicts. The record is
read again and the outcome applied to what is there now: a charge that went
through on a subscription just cancelled is recorded and reported, and the
subscription stays cancelled.

## When an instance dies mid-charge

Its claim expires after `leaseMs`, and another instance claims the renewal. It
decides the same charge — same period, same attempt — and so sends the same
idempotency key. The payment provider answers with the original payment instead
of charging again, and the renewal completes as if nothing had happened.

That is the second guard. The first, the claim, means the provider normally never
sees the second request at all.

## Several instances

Nothing is held in memory that another instance needs. Each instance has its own
claim identity, sweeps on its own, and delivers the events of the records it
processed to the handlers registered in it. Any number can run against one
database.

## Testing the clock

The clock the module reads is replaceable (`UseClock`), and the suite drives a
manual one through trials, renewals, failures, retries and period ends. The real
triggers are tested separately in real time: a renewal made by polling with
nobody calling, and — with Redis — a task scheduled for a trial end and fired by
Redis while the sweep is an hour away, and a task deleted from Redis whose
renewal the sweep still makes. A boot test launches a project the production
way, without the test harness, and checks it starts and renews.
