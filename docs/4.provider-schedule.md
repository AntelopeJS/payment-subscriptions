# The provider schedule

This module always owns the clock. Some providers that leave the merchant to
fire each charge will still store the schedule, and handle the authentication
chain between charges, if asked. Mangopay's Recurring PayIn Registration stores
frequency, dates and amounts and chains the customer-initiated first payment to
the merchant-initiated ones; Mangopay still does not fire them.

For those, part of a subscription's state can live with the provider as well as
in this module's database. The seam for it is `ProviderSchedule`:

| Call       | When                                           | The default                    |
| ---------- | ---------------------------------------------- | ------------------------------ |
| `register` | Once, as a subscription is created             | Records nothing                |
| `charge`   | Each time a period is charged                  | An off-session `CreatePayment` |
| `release`  | Once, when a subscription ends, for any reason | Does nothing                   |

What `register` returns is stored with the subscription and handed to every
`charge` and `release`. A schedule never decides when to charge, and never
throws for a decline: a declined charge resolves with a `failed` payment, as
`CreatePayment` does.

`register` runs before the subscription is stored and is given no idempotency
key, so two creations racing on one key may both call it. A schedule that
registers anything real must tolerate that, or derive its own key from the
subscription identifier it is handed.

The schedule is chosen by the `providerSchedule` setting. Only the default,
`payment-interface`, exists. A Mangopay schedule would charge against the
registration through the Mangopay module's own interface, which is the escape
hatch for provider-specific behaviour everywhere else in AntelopeJS.
