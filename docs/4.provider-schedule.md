---
title: The provider schedule
description: Why the module can mirror part of a subscription with a provider such as Mangopay, and how the providerSchedule extension point works.
mode: explanation
---

This module always owns the clock. Some providers leave the merchant to fire
each charge, but still store the schedule if asked, and handle the
authentication chain between charges. The Recurring PayIn Registration of
Mangopay stores the frequency, the dates, and the amounts. It chains the first
payment, which the customer starts, to the later payments, which the merchant
starts. Mangopay still does not fire those payments.

For those providers, part of the state of a subscription can live with the
provider as well as in the database of this module. The extension point for it
is the `ProviderSchedule` interface in `src/schedule.ts`:

| Call       | When                                           | The default                    |
| ---------- | ---------------------------------------------- | ------------------------------ |
| `register` | Once, as a subscription is created             | Records nothing                |
| `charge`   | Each time a period is charged                  | An off-session `CreatePayment` |
| `release`  | Once, when a subscription ends, for any reason | Does nothing                   |

The module stores what `register` returns with the subscription, and hands it
to every `charge` and `release` call. A schedule never decides when to charge.
It never throws for a decline either. A declined charge resolves with a
`failed` payment, as `CreatePayment` does.

`register` runs before the module stores the subscription, and it receives no
idempotency key. Two creations that race on one key can therefore both call
it. A schedule that registers anything real must tolerate that, or derive its
own key from the subscription ID that it receives.

The `providerSchedule` setting chooses the schedule. Only the default,
`payment-interface`, exists. Any other name makes the module throw at
construction, with an error that lists the known names. A Mangopay schedule
would charge against the registration through an interface of the Mangopay
module itself. Everywhere else in AntelopeJS, provider-specific behaviour also
goes through the interface of the provider module, not through the portable
interfaces.
