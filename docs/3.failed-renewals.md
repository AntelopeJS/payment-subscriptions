# Failed renewals

The interface promises only that a failed renewal is reported as `past_due`. What
happens next is each implementation's policy. This is this module's.

## The policy

When charging a period is declined:

1. The period advances anyway, the subscription goes `past_due`, and
   `subscription.payment_failed` is raised. The unpaid period is the current one.
2. It is retried after each entry of `retryDelaysMs`, measured from the failure
   before it. By default: one day, three days, seven days — four attempts over
   eleven days.
3. A retry that succeeds makes it `active` again, in the same period. The cycle
   does not move.
4. When the last retry fails, the subscription ends: `canceled`, with
   `endReason: "payment_failed"`, and both `subscription.payment_failed` and
   `subscription.canceled` are raised.

Each new attempt uses the subscription's payment method at the time it is made,
so `UpdateSubscriptionPaymentMethod` during `past_due` is how a payer recovers.
Each attempt has its own idempotency key; a retry is a new charge, not a replay
of the decline.

A subscription set to end at period end keeps being retried until its period
ends, and then ends instead of being retried further.

## A charge that is still settling

A bank debit can report `pending` for days. The subscription stays as it was —
`active` after a trial or a paid period, `past_due` during retries — and the
charge is read again every `settlementPollMs` until it settles, then treated as
succeeded or declined. Nothing is reported until it settles.

If the subscription is cancelled while a charge is settling, the charge is still
followed; a charge that then succeeds is recorded and reported, so the money can
be refunded.

## A provider that refuses the charge

`CustomerNotFoundError`, `PaymentNotFoundError`, `InvalidPaymentStateError` and
`UnsupportedOperationError` from the payment interface mean the provider will
not make this charge — most often because the saved method has been removed.
They count as a declined attempt: `past_due`, retried under the policy, ended
when the retries are spent. The `subscription.payment_failed` event has no
`payment`, since none was made.

## A provider that cannot be reached

Any other `PaymentError` is not a decline: the charge is in doubt. The same
attempt can be made again after `errorBackoffMs` only within its persisted
provider guarantee, with the same idempotency key **and the same payment method**,
recorded before the first try — so if the first request did reach the provider,
the retry finds that charge instead of making another, even if the method was
changed meanwhile. The new method is used from the next attempt.

If the subscription is cancelled while a charge is in doubt, the attempt is not
made again. A charge that did land then reaches the merchant only as the payment
interface's `payment.succeeded` webhook, carrying `antelopeSubscription`.

## After a stall

Periods are anchored, so a subscription that could not be processed for longer
than a period — the database or every instance was down — has every missed
period charged on recovery, one after another.

## The first period

The first period is charged inside `CreateSubscription`, and a decline there
creates nothing: it rejects with `SubscriptionPaymentError`. A payer with no
subscription is not `past_due`.

A creation that ends without an answer — the provider could not be reached, or
the instance died mid-call — must be replayed with the same idempotency key.
The replay resumes it only within its persisted replay window. After expiry it
rejects with a reconciliation-required error naming the subscription ID,
without charging again. A refused creation remains refused on replay.
A creation nobody replays is never completed by the module, and a charge it made
belongs to no subscription; it still reaches the merchant as a payment-interface
webhook carrying `antelopeSubscription`.

## Reconciliation and operational recovery

`guaranteedReplayMs` defaults to zero: the first call is allowed, but an uncertain
result is not blindly replayed. Set a positive value only from a documented
provider guarantee that covers every account using this module, with a safety
margin. Transient errors are retried only strictly before the saved deadline;
declines follow the separate finite `retryDelaysMs` policy with new attempt keys.

Live subscriptions expose `reconciliationRequired`, `attemptStartedAt`,
`attemptReplayUntil` and `phase` in `vendorData`. A halted record has no next
charge scheduled. Cancellation and payment-method changes do not clear that
hold. Initial creations expose the hold through the replay error and persisted
record because they are not yet public live subscriptions.

For operational recovery:

1. Stop all module instances/triggers and drain in-flight requests. Back up the
   record and retain its revision, provider account, attempt key, timing and
   payment method. Never delete the record or reset timing to force a replay.
2. Search the provider's authoritative ledger, including webhooks and metadata
   `antelopeSubscription`, using the original account and attempt key. If the
   result is still unknown, leave the hold in place and escalate to the provider.
3. If a payment is found, verify its customer, method, amount, currency,
   subscription metadata and original attempt key. Recover the target period
   index from that key (`payment-subscriptions:<id>:<period>:<attempt>`), not
   from the record's last paid period. If the target cannot be established,
   leave the hold in place.
   An operator-reviewed, revision-conditional database repair can attach that ID
   as `pendingPayment`, clear `reconciliationRequired`, and set `nextActionAt`
   and `dueAt` to now with the lease cleared. Set `periodIndex` to the recovered
   target for every record, including renewals; the initial charge targets `0`.
   For a `creating` record, replay the original creation key: it reads that
   payment instead of charging. For a live
   record, restart processing to read and apply its actual status. Keep the
   original attempt identity and timing intact.
4. If the provider conclusively proves no charge exists, prefer retiring the
   held subscription and creating a replacement with a new key under an audited
   merchant decision. Do not silently retry the uncertain attempt. Resolve any
   provider schedule registration as well. Refunds and entitlement corrections
   remain merchant operations.

There is intentionally no portable force-retry or reconciliation API. Database
repair requires provider-specific evidence and an audit trail; an elapsed lease,
a method update or a longer configuration value is not evidence of non-payment.
