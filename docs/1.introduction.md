# Introduction

`@antelopejs/payment-subscriptions` implements
`@antelopejs/interface-subscriptions` for any provider wired behind
`@antelopejs/interface-payment`. It is the implementation for providers that
leave each renewal charge to the merchant — Adyen, Checkout.com, Mangopay — and
it is an explicit fallback. Stripe users should use Stripe's native subscription
implementation by default rather than run two competing renewal engines.

## What it needs

| Interface                               | Why                                                           | Required |
| --------------------------------------- | ------------------------------------------------------------- | -------- |
| `@antelopejs/interface-payment`         | Every charge is an off-session payment against a saved method | Yes      |
| `@antelopejs/interface-database`        | Every subscription is a record there, and nowhere else        | Yes      |
| `@antelopejs/interface-redis-scheduler` | Fires each renewal on time instead of within one poll         | No       |

The database adapter must implement `atomicMutation`, the interface-database
conditional single-record write. `@antelopejs/mongodb` implements it, and the suite
runs against it.

## What it charges

Each period is one `CreatePayment` with `offSession: true` against the
subscription's saved method, under the subscription's `reference`, with the
subscription's metadata plus `antelopeSubscription` set to its identifier. The
idempotency key is
`payment-subscriptions:<subscription>:<period>:<attempt>`: stable across
anything that might repeat a charge, and different for each deliberate retry.

The optional `provider` passed when a subscription is created selects the
payment account, exactly as on the payment interface, and is stored with the
subscription: every later charge goes to the same account, because the
customer and the method exist only there. Reading the subscription back needs
the same `provider`.

## What it records

One record per subscription, in the schema `payment-subscriptions`, table
`subscriptions`, default instance:

- the request — customer, method, amount, interval, reference, metadata;
- the billing state — anchor, current period, status, attempt, the latest
  charge and any charge still settling;
- `nextActionAt`, when it next needs attention, and `dueAt`, what the sweep
  queries: the same, or now while events are waiting;
- the claim — which instance holds it, and until when;
- the attempt's persisted start and replay deadline, and any reconciliation hold;
- the outbox — events raised but not yet delivered;
- the idempotency keys of recent cancellations and method changes.

A subscription's identifier is derived from the creation's idempotency key and
the `provider`, which is what lets two racing creations with one key find each
other.

## Events

Each change records its events in the same write as the change itself, and they
are delivered from there to the handlers registered on `SubscriptionEvents`.
Delivery is retried until every handler accepts, so it is at least once, and an
event survives a crash between the change and its delivery.
