`@antelopejs/payment-subscriptions` implements
`@antelopejs/interface-subscriptions` for any provider wired behind
`@antelopejs/interface-payment`. It is the implementation for providers that
leave each renewal charge to the merchant, such as Adyen, Checkout.com, and
Mangopay. It is a fallback that you choose explicitly. Stripe users should use
the native subscription implementation of Stripe by default, so that two
renewal engines never compete.

## What it needs

| Interface                               | Why                                                           | Required |
| --------------------------------------- | ------------------------------------------------------------- | -------- |
| `@antelopejs/interface-payment`         | Every charge is an off-session payment against a saved method | Yes      |
| `@antelopejs/interface-database`        | Every subscription is a record there, and nowhere else        | Yes      |
| `@antelopejs/interface-redis-scheduler` | Fires each renewal when it is due instead of at the next poll | No       |
| `@antelopejs/interface-redis`           | The module uses the scheduler only when Redis is also wired   | No       |

The database adapter must implement `atomicMutation`, the conditional
single-record write of `@antelopejs/interface-database`. `@antelopejs/mongodb`
implements it, and the suite runs against it.

## What it charges

Each period is one `CreatePayment` call with `offSession: true` against the
saved method of the subscription. The call carries the `reference` of the
subscription and its metadata, plus `antelopeSubscription` set to the
subscription ID. The idempotency key is
`payment-subscriptions:<subscription>:<period>:<attempt>`. The key stays the
same for anything that might repeat a charge, and changes for each deliberate
retry.

The optional `provider` that you pass when you create a subscription selects
the payment account, as on the payment interface. The module stores it with
the subscription, and every later charge goes to the same account, because the
customer and the method exist only there. To read the subscription back, pass
the same `provider`.

## What it records

The module keeps one record per subscription, in the schema
`payment-subscriptions`, table `subscriptions`, on the default instance. The
record holds:

- The request: customer, method, amount, interval, reference, description, and
  metadata.
- The billing state: anchor, current period, status, attempt, the latest
  charge, and any charge still settling.
- `nextActionAt`, when the subscription next needs attention, and `dueAt`, the
  field that the sweep queries. `dueAt` equals `nextActionAt`, or now while
  events wait for delivery.
- The claim: which instance holds it, and until when.
- The persisted start and replay deadline of the current attempt, and any
  reconciliation hold.
- The outbox, which holds the events raised but not delivered yet.
- The idempotency keys of the last 50 cancellations and payment method changes.

The subscription ID is `sub_` followed by a hash of the idempotency key of the
creation and the `provider`. Two creations that race with one key therefore
find the same record.

## Events

Each change records its events in the same write as the change itself. The
module delivers them from there to the handlers registered on
`SubscriptionEvents`, in order. If a handler rejects an event, delivery stops
at that event and the module tries again after `errorBackoffMs`, until every
handler accepts. Delivery is at least once, and an event survives a crash
between the change and its delivery.
